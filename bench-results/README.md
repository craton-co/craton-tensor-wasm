# bench-results/

Committed bench artifacts consumed by the CI regression gate. Anything
here is read by [`.github/workflows/bench.yml`](../.github/workflows/bench.yml)
on PRs that touch `crates/tensor-wasm-bench/**` or `crates/*/src/**`, and the
build fails when measured medians exceed the per-metric ceiling.

## Files

- **`baseline.json`** — committed median + tolerance per tracked Criterion
  metric. One entry per `(group, id)` pair. See "Metric inventory" below
  for what each entry maps back to.
- **`baseline-notes.md`** — running log of bench-id renames, additions,
  removals, and other things the regression-gate Python parser needs to
  know about across releases. Read this before editing `baseline.json`.
- **`tail-latency.json`** — P50 / P95 / P99 / **P99.9** / max snapshot for
  the dispatch and e2e hot paths, generated by
  [`crates/tensor-wasm-bench/benches/tail_latency.rs`](../crates/tensor-wasm-bench/benches/tail_latency.rs).
  **Not** consumed by the regression gate; this is a long-tail observability
  artefact for the v0.3 "Production observability" milestone in
  [`docs/PATH-TO-V1.md`](../docs/PATH-TO-V1.md). Criterion's default
  reporter only publishes mean / std-dev / median, so this sidecar exists
  to fill the P99.9 gap. See [Tail-latency artefact](#tail-latency-artefact)
  below for the schema and the regeneration recipe.
- **`dispatch-future-backends.json`** — F3 scaffold artefact: P50 / P95 /
  P99 / P99.9 / max for the existing busy-poll `DispatchFuture` path
  vs the future `cuda-async`-backed alternative tracked by
  [RFC 0001](../rfcs/0001-cuda-oxide-integration.md) Unresolved question
  #3 ("Does cuda-async's Tokio integration outperform our hand-rolled
  `DispatchFuture` busy-poll?"). **Today** the file holds one measured
  line (busy-poll) plus one `"status":"skipped"` line for cuda-async; the
  v0.4 cuda-oxide port replaces the skip with real numbers without
  changing the schema. Generated by
  [`crates/tensor-wasm-bench/benches/dispatch_future_backends.rs`](../crates/tensor-wasm-bench/benches/dispatch_future_backends.rs).
  **Not** consumed by the regression gate — diagnostic only. See
  [Dispatch-future backend comparison](#dispatch-future-backend-comparison)
  below for the schema, the skip-line convention, and the regeneration
  recipe.

## Re-baselining

Run a clean local pass and save it as a named baseline:

```sh
# Per-bench (recommended — easier to spot per-file regressions):
cargo bench -p tensor-wasm-bench --bench cold_start       -- --save-baseline new
cargo bench -p tensor-wasm-bench --bench kernel_dispatch  -- --save-baseline new
cargo bench -p tensor-wasm-bench --bench memory_bandwidth -- --save-baseline new
cargo bench -p tensor-wasm-bench --bench jit_compile      -- --save-baseline new
cargo bench -p tensor-wasm-bench --bench e2e_inference    -- --save-baseline new
cargo bench -p tensor-wasm-tenant --bench context_switch  -- --save-baseline new

# Or whole-workspace if you trust the host:
cargo bench --workspace -- --save-baseline new
```

Then inspect `target/criterion/<group>/<id>/new/estimates.json` (or the
HTML at `target/criterion/<group>/<id>/report/index.html`) and copy each
median into `baseline.json`. Update `baseline-notes.md` with any
group/id renames or coverage changes. Submit the re-baseline as its own
commit, separate from any behavioral change, so future bisects can
attribute regressions cleanly.

## How CI consumes this

The `bench` workflow at [`.github/workflows/bench.yml`](../.github/workflows/bench.yml)
parses Criterion's `--output-format bencher` lines, joins them against
`baseline.json` by `<group>/<id>`, and fails the build when
`measured_median > baseline.median_ns * (1 + (tolerance_pct + regress_pct_threshold) / 100)`.
The published policy is in [`docs/PERFORMANCE.md`](../docs/PERFORMANCE.md).

`tail-latency.json` is **not** read by the regression gate — it is a
diagnostic snapshot, refreshed manually when the underlying paths change.

## Tail-latency artefact

Criterion exposes mean, std-dev and median by default but not P99.9, and
its ~100-sample default is too small to resolve a meaningful P99.9 (a
single sample at the tail moves the estimate by ~1 ppt of the population).
The `tail_latency` bench takes 10 000 raw observations per metric, sorts
them once, and reads percentiles via the nearest-rank rule
(`samples[ceil(p * n) - 1]`).

### Metrics covered

| Metric | Mirrors | Source |
|---|---|---|
| `dispatch/serial/100` | `kernel_dispatch::bench_serial` (back-pressure cap=1) | `crates/tensor-wasm-bench/benches/tail_latency.rs` |
| `dispatch/concurrent_cap64/100` | `kernel_dispatch::bench_concurrent` (cap=64, 4-worker rt) | same |
| `e2e/healthz/get` | `e2e_inference::bench_healthz` | same |
| `e2e/invoke_not_found/post` | `e2e_inference::bench_invoke_not_found` | same |

### Schema

```json
{
  "// generated": "P99.9 tail-latency snapshot (see crates/tensor-wasm-bench/benches/tail_latency.rs).",
  "// algorithm": "nearest-rank percentile per ISO/IEC 25062 over 10000 sorted samples per metric",
  "// backend-axis": "W4.4 RFC 0001 extension -- run the bench once per backend (default / --features cudarc-backend / --features cuda-oxide-backend) and diff the three files; see docs/BENCHMARKING.md for the operator recipe",
  "backend": "unified-memory",
  "metrics": [
    {
      "metric": "dispatch/serial/100",
      "backend": "unified-memory",
      "samples": 10000,
      "p50_ns": ...,
      "p95_ns": ...,
      "p99_ns": ...,
      "p99_9_ns": ...,
      "max_ns": ...
    }
  ]
}
```

The `backend` field appears both at the top level (so a reader sees the
compile-time slot the run targeted without scanning every metric) and on
every per-metric entry (so a downstream parser joining many files by
`<metric, backend>` doesn't have to reach back into the document root).
The redundant per-metric field is intentional — wave-4 ops work
formalises this schema and may keep both or demote the per-metric one
once the regression-gate parser is updated. **For W4.4 the schema is
treated as forward-compatibility-only**, and the per-W4.4 deprecation
note in `tail_latency.rs` calls out that downstream parsers pre-dating
W4.4 should treat `backend` as optional and fall back to
`"unified-memory"` when the field is missing (matches the historical
W4.6 default before the backend axis was added).

### Regenerate

The bench is now backend-aware (W4.4 — RFC 0001 Unresolved questions
extension). Running it with no features produces a `unified-memory`-
labeled file; flip features to retarget the label:

```sh
# unified-memory (historical default, the cust-backed path):
cargo bench -p tensor-wasm-bench --bench tail_latency

# cudarc (label-only at the bench layer — see the bench Cargo.toml
# comment for why this doesn't forward to tensor-wasm-mem/cudarc-backend):
cargo bench -p tensor-wasm-bench --bench tail_latency --features cudarc-backend

# cuda-oxide (the v0.5 cust successor scaffold from RFC 0001;
# requires libclang for cuda-bindings' build script):
cargo bench -p tensor-wasm-bench --bench tail_latency --features cuda-oxide-backend
```

Each run overwrites `bench-results/tail-latency.json` (cwd-aware), so
operators capturing all three backends should rename between runs —
the documented recipe is in
[`docs/BENCHMARKING.md#tail-latency`](../docs/BENCHMARKING.md#tail-latency).
The bench also emits one `TAIL_LATENCY {...}` JSON line per metric to
stdout regardless (CI captures via grep), each line carrying its own
`"backend":` field so a single CI log can be split by backend after the
fact.

The bench is wall-clock-cheap (10 000 × ~6 µs per dispatch sample plus
warm-up ≈ a few seconds per metric) so re-running on every observability
PR is reasonable; it is intentionally not on the CI regression-gate path
because tail metrics on shared CI runners are too noisy to gate on
without hand-tuning thresholds per metric.

## Dispatch-future backend comparison

The `dispatch_future_backends` bench answers
[RFC 0001](../rfcs/0001-cuda-oxide-integration.md) Unresolved question #3
— whether `cuda-async`'s Tokio integration outperforms the hand-rolled
busy-poll `DispatchFuture` in
[`crates/tensor-wasm-wasi-gpu/src/async_dispatch.rs`](../crates/tensor-wasm-wasi-gpu/src/async_dispatch.rs).
The bench runs two `DispatchFutureBackend` impls over a no-op dispatch
loop (acquire back-pressure permit → await future → drop) using the same
W4.6 nearest-rank percentile machinery and writes one line per backend.

**Today's status.** The `busy-poll` backend produces real numbers; the
`cuda-async` backend is a documented stub that emits a
`"status":"skipped","reason":"cuda-async-backend: not yet wired -- see
RFC 0001 v0.4 port"` line until the v0.4 cuda-oxide port wires it. The
schema is forward-compatible — the v0.4 author replaces the skip line
with a `"status":"measured"` line that has the same shape as the
`busy-poll` line, and nothing downstream needs to change.

### Schema

```json
{
  "// generated": "BusyPoll vs cuda-async DispatchFuture comparison (see crates/tensor-wasm-bench/benches/dispatch_future_backends.rs).",
  "// rfc": "rfcs/0001-cuda-oxide-integration.md -- Unresolved question #3",
  "// algorithm": "nearest-rank percentile per ISO/IEC 25062 over 10000 sorted samples per backend",
  "backends": [
    {
      "backend": "busy-poll",
      "status": "measured",
      "samples": 10000,
      "p50_ns": ..., "p95_ns": ..., "p99_ns": ..., "p99_9_ns": ..., "max_ns": ...
    },
    {
      "backend": "cuda-async",
      "status": "skipped",
      "reason": "cuda-async-backend: not yet wired -- see RFC 0001 v0.4 port"
    }
  ]
}
```

### Regenerate

```sh
# Today (busy-poll numbers, cuda-async skipped):
cargo bench -p tensor-wasm-bench --bench dispatch_future_backends --features cuda

# v0.4 once the cuda-async path is wired (real numbers for both backends).
# The `cuda-oxide-backend` feature pulls in the cuda-async dep via
# tensor-wasm-mem and requires the nightly-2026-04-03 toolchain override
# documented in docs/CUDA-SETUP.md.
RUSTUP_TOOLCHAIN=nightly-2026-04-03 \
  cargo bench -p tensor-wasm-bench --bench dispatch_future_backends \
    --features cuda,cuda-oxide-backend
```

Without `--features cuda` the bench compiles and runs, but both backends
emit skip lines so the file is regenerated as two skips. That mode is
useful only to verify the bench builds on a non-CUDA host.

Like `tail-latency.json`, this file is **not** read by the regression
gate — it is a diagnostic snapshot, refreshed when either the busy-poll
path in `async_dispatch.rs` or the cuda-async stub changes.
